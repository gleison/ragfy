# Ragfy architecture

The Go daemon assembled in `cmd/ragfy` is the active runtime. Application code lives under `internal`: `service` owns the use cases and HTTP API, `knowledge` defines the persistence contract, `storage/sqlite` implements that contract, `model` defines independent generation and embedding capabilities, `extraction` coordinates and routes generative extraction, `reconciliation` classifies relationships between new and earlier knowledge, `chunking` splits documents, `retrieval` owns similarity and ranking, `digest` validates extracted knowledge, `hook` integrates Codex and Claude, and `platform` handles operating-system concerns. Hook processes are intentionally short-lived and send JSON with an explicit provider source to a token-protected loopback API.

Digest generation uses the CLI for the provider that created the session: `codex exec` for Codex and `claude -p` for Claude. Both implement the same `model.Generator` contract and run without tools, hooks, writes, or session persistence. Extraction accepts only complete JSON with all four arrays, rejects schema placeholders and transient runtime observations, and requires every record to cite exact transcript evidence. A preference or decision can be explicit in a user message or implicitly accepted when an assistant claim is followed by a later user action that clearly relies on it; both quotes are retained. Each extracted record is classified with global or project visibility based on the knowledge itself, not merely the session origin. The service supplies the complete conversational spine, excluding tools, reasoning and injected runtime context. A spine that exceeds the provider-safe limit is split only at message boundaries with overlapping messages; the window candidates are then consolidated and validated against the complete spine. Each category can retain up to four strong records. Inspect extracted content when validating changes, not just document counts or worker completion logs.

After extraction and embedding, reconciliation selects a small set of semantically close active transcript records with the same kind, scope and project. The provider that created the session classifies only high-confidence duplicate or supersession relationships; complementary, merely related and ambiguous records remain independent. Problems are never superseded by similarity. Transcript timestamps, with file modification time only as a fallback, determine chronology so a late-processed old session cannot replace newer knowledge. Superseded records remain in SQLite with their winner and reason, but searchable corpus queries return only active records. Replacing one session, restoring records that depended on its former winners, storing new records, applying supersessions and updating the transcript hash occur in one repository transaction.

The setup wizard recommends `Qwen/Qwen3-Embedding-0.6B-GGUF/Qwen3-Embedding-0.6B-Q8_0.gguf` for multilingual embeddings, using `last` pooling and an English retrieval instruction on queries. A user can instead select another GGUF URI; custom models use their declared pooling and no query prefix. Setup validates custom models by loading them in embedding mode and checking test vectors, then pins their computed SHA-256.

The default hybrid retriever generates up to 12 candidates using semantic similarity and field-aware BM25, with title terms weighted above content and a small current-project boost. It applies an absolute and relative relevance cutoff, then MMR diversity before returning at most four records. Ranking logs expose candidate IDs, scope, selection status and score components without copying knowledge content.

The app downloads the missing embedding GGUF into its application data directory and checks its pinned SHA-256 value before loading. It tracks the embedding model version in the repository and re-embeds stored documents when that version changes. The enabled providers come from `config.json`; only selected provider executables and routers are composed in `cmd/ragfy`. The service depends on the `extraction.Extractor` and `reconciliation.Reconciler` interfaces. `knowledge.Repository` is the persistence boundary; `storage/sqlite.Repository` is the first implementation and is also selected only in composition. Generation, embedding, extraction, reconciliation, chunking and retrieval are separate dependencies. A Supabase adapter can implement persistence and a database-native retriever without changing the service package.

`ragfy setup` interactively selects the embedding model and one or both clients, reconciles their `UserPromptSubmit` and `SessionEnd` hooks, registers the background service, and waits for a healthy response. Operational commands require the saved setup configuration; running `ragfy` without arguments produces the same diagnostic report as `ragfy status`. Status combines service health and repository statistics with local inspection of the binary, model cache, configured clients, hook commands, and their executable path. Tagged releases build ready-to-run macOS and Linux archives plus the installer for both amd64 and arm64; source builds remain a development workflow. `ragfy update` retrieves the installer from the latest release instead of a source branch. `ragfy uninstall` removes the service and Ragfy hooks while preserving local data. `ragfy search <phrase>` exposes the same hybrid retrieval used by prompt hooks. Search returns global knowledge plus knowledge scoped to the current working-directory or explicitly selected project. `ragfy ingest <folder>` indexes Markdown, RST, and text files without generative extraction, while `ragfy ingest --text <text>` stores a manual memory; `--project <name>` restricts either form to one project.
